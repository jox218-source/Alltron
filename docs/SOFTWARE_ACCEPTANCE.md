# Software-only acceptance checklist

Evidence date: 2026-10-02. Acceptance status: partial implementation; software-only owner and Linux deployment gates remain open. The local owner session, Home Assistant setup UI, and Linux service command interface exist, but their presence does not mean acceptance passed. A lead-reported baseline of 111 passing tests predates the Linux installer changes; it is not a current full-suite count. No post-installer full-suite result, disposable Linux service rehearsal, or independent owner trial is recorded here. This checklist defines the software gate before separate-hardware acceptance. A checked box requires a dated run record, software and image versions, sanitized logs/results, and the disposable environment description. A plan, fake test, or local preview alone does not count as a pass.

## Disposable Linux owner trial

- [ ] **API owner lifecycle and browser request protection.** In a disposable install, verify login, session expiry, logout, server-side session revocation, and CSRF rejection for state-changing requests. Verify expired, logged-out, revoked, and forged requests fail closed and expose no credential or session secret. Record the tested endpoints, expected/observed outcomes, and sanitized evidence.
- [ ] **Home Assistant over verified TLS.** Provision a disposable Home Assistant instance and synthetic entities only. Verify the configured endpoint's TLS certificate and service identity before sending credentials; reject invalid, untrusted, expired, or mismatched identity. Exercise owner onboarding/authorization, explicit entity selection, allowed synthetic actions, credential expiry and revocation, HA outage and recovery. Confirm disallowed entities/actions fail closed and secrets never reach browser responses, logs, or diagnostics.
- [ ] **Isolated Codex execution.** Use an isolated Linux user or container with a fresh owner login created for this trial, a dedicated profile/config directory, restricted filesystem and network access, bounded output and runtime, and cleanup. Do not reuse the developer's Codex profile. Verify benign answer flow, timeout/cancellation, authentication and network failures, denied filesystem/network probes, no route from output to HA actions, and removal/revocation of the trial login and temporary state. Record isolation controls and cleanup evidence.
- [ ] **Linux services and installer lifecycle.** From a clean disposable VM, run installer preflight and record plain-language results. Install services, repeat the install, exercise a failed update and rollback, and uninstall. Verify idempotence, service identity/permissions, and that rollback/uninstall preserve and can restore owner household state. Verify uninstall removes application binaries and temporary data while clearly reporting any owner data or credentials that require separate removal. The [Linux service command interface](LINUX_SERVICES.md) is implemented, but live preparation, service lifecycle, update/recovery, and owner acceptance remain untested.
- [ ] **Setup wizard clarity.** Have a first-time owner follow the wizard without developer assistance. Verify each screen explains what is needed, why, what success looks like, and a concrete recovery step on failure; credentials stay out of the browser and diagnostics. Exercise authorization denial, expired/revoked access, unavailable services, missing prerequisites, and retry/recovery. Record unclear steps and resolve them before acceptance.
- [ ] **Independent VM owner trial.** A person other than the implementer, using a fresh VM snapshot and a separate owner account/profile, completes the documented install, setup, synthetic HA action, harmless Codex answer (if enabled), recovery exercise, and uninstall/state-preservation check without private project data or developer credentials. Capture the exact docs/release version and observed blockers.

## Separate hardware gate

- [ ] **Hardware acceptance remains a separate required gate.** After software-only acceptance, use a separately identified and explicitly allowlisted test Pi to validate the supported hardware/OS profile, audio devices, live wake/STT/TTS path, full-load resource use, and physical recovery behavior. VM success does not establish Pi compatibility, latency, acoustic quality, or hardware support. See [speech provenance](SPEECH_PROVENANCE.md) and [stage plan](STAGES.md).
